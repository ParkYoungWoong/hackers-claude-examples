# 하네스 엔지니어링 일관성 데모

> 같은 과제를 클로드 코드에 주었을 때, **하네스 엔지니어링 전(before)에는 결과가 제각각 갈리고, 후(after)에는 누가 해도 같은 구조가 나온다**는 것을 직접 체험하는 데모.

## 한 줄 요약

하네스 엔지니어링은 "AI가 알아서 잘하기"를 "프로젝트가 정한 방식대로만 한다"로 바꾼다. 그 결과가 **일관성**(매번 같은 구조)과 **안정성**(매번 통과하는 품질)이다.

## 브랜치 구성

| 브랜치    | 의미   | 하네스                                                                                                                  |
| --------- | ------ | ----------------------------------------------------------------------------------------------------------------------- |
| `main`    | before | 아키텍처 수준 CLAUDE.md만. 기능 구현 방식 규칙 없음.                                                                    |
| `harness` | after  | 기능 규칙(CLAUDE.md) + 자동 로드 규칙(.claude/rules) + 검증 훅(포맷/린트/타입) + 차단 훅(hookify) + 전용 스킬 + vitest. |

두 브랜치 모두 **과제 기능(삭제/완료 토글)은 미구현 상태**다. 수강생이 양쪽에서 직접 구현한다.

## 진행 순서

### 1단계: before에서 갈림 관찰 (`main`)

```bash
git checkout main
```

`assignment.md`의 과제 프롬프트를 클로드 코드에 입력한다. **여러 번**(권장 3회, 매번 변경을 되돌리고 다시) 반복한다. 매 실행 결과를 비교한다.

관전 포인트(`decision-points.md`의 표와 대조):

- 삭제 버튼을 `Button.tsx`로 썼나, raw `<button>`으로 썼나?
- `Todo` 타입에 `completed`를 넣었나, UI에서만 처리했나?
- 콜백 이름이 `onDelete`인가 `onRemove`인가 `onClick`인가?
- 완료 표시가 취소선인가 체크박스인가 배경색인가?
- 상태 로직이 `App.tsx`인가 커스텀 훅인가?
- 코드 스타일(따옴표, 세미콜론, 줄바꿈)이 매번 같은가?

→ 실행마다 선택이 달라진다. **정답이 정해져 있지 않기 때문이다.**

매 실행 후 되돌리기:

```bash
git restore .
```

### 2단계: after에서 일관성 관찰 (`harness`)

```bash
git checkout harness
```

**똑같은** 과제 프롬프트를 입력한다. 마찬가지로 여러 번 반복한다.

이번에는:

- `CLAUDE.md`의 "기능 개발 규칙"과 `.claude/rules`(코드 스타일/보안/테스트)가 모든 선택을 하나로 고정한다.
- 파일을 편집할 때마다 검증 훅이 Prettier 포맷을 **자동 적용**하고, 린트/타입 위반은 피드백으로 돌려준다.
- 위험 API(`dangerouslySetInnerHTML`/`eval` 등)를 쓰면 hookify 차단 훅이 편집을 막는다.
- `implement-feature`/`tested-component` 스킬이 구현·테스트 워크플로우를 캡슐화하고, 새 컴포넌트엔 `vitest` 테스트가 동반된다.

→ 실행마다 **같은 구조**가 나온다. 버튼 컴포넌트, `completed` 필드, `onDelete`/`onToggle`, 취소선, 코드 스타일까지 동일하다.

### 3단계: 차이 정리

before 결과들과 after 결과들을 나란히 놓고, "무엇이 일관성을 만들었는지"를 `why-consistency.md`로 정리한다.

## 자료 구성

- `README.md` (이 문서) - 데모 진행 가이드
- `assignment.md` - 양 브랜치에 공통으로 줄 과제 프롬프트
- `decision-points.md` - 결과가 갈리는 의사결정 지점과 after 고정 규칙
- `why-consistency.md` - 하네스 각 계층이 일관성/안정성에 기여하는 메커니즘
