# 결과가 갈리는 의사결정 지점

"삭제 + 완료 토글" 과제 하나에도, 정답이 정해지지 않은 결정이 최소 7개 숨어 있다. before에서는 클로드가 매번 이 중 하나를 임의로 고르기 때문에 결과가 갈린다. after에서는 `CLAUDE.md`의 "기능 개발 규칙"이 각 결정을 하나로 고정한다.

| 의사결정 지점    | before: 갈리는 선택지                                    | after: 고정 규칙                                                       |
| ---------------- | -------------------------------------------------------- | ---------------------------------------------------------------------- |
| 삭제 버튼 구현   | raw `<button>` 직접 작성 vs 기존 `Button.tsx` 재사용     | `Button.tsx` 사용. `variant="danger"`, `size="small"`, `icon="delete"` |
| 완료 상태 데이터 | `Todo` 타입에 필드 추가 vs 별도 상태 vs UI에서만 처리    | `src/types.ts`의 `Todo`에 `completed: boolean` 추가, 생성 시 `false`   |
| 완료 표시 UI     | 취소선 / 체크박스 / 배경색 / 흐리게 - 제각각             | `todo-item--done` 클래스 + 취소선. 텍스트 클릭으로 토글                |
| 콜백 네이밍      | `onDelete`/`onRemove`, `onToggle`/`onComplete`/`onCheck` | `onDelete(id: string)`, `onToggle(id: string)`                         |
| Props 타입 위치  | 컴포넌트 로컬 vs `types.ts` 중앙화 - 혼재                | 도메인 타입은 `types.ts`, 컴포넌트 Props는 파일 상단 로컬 `type Props` |
| 상태 변경 위치   | `App.tsx` 인라인 vs 커스텀 훅 분리 vs 전역 스토어        | `App.tsx` 인라인, 불변 갱신(삭제 `filter`, 토글 `map`)                 |
| export 방식      | named vs default                                         | default export 유지                                                    |

## 왜 이게 문제인가

각 결정 자체에는 "절대적 정답"이 없다. raw 버튼도 동작하고, 체크박스도 완료를 표현한다. 문제는 **사람(혹은 실행)마다 다른 선택을 한다는 것**이다. 그 결과:

- 코드 리뷰에서 매번 "이건 이렇게 하기로 했잖아요"가 반복된다.
- 같은 프로젝트인데 파일마다 패턴이 달라 읽기 어렵다.
- 재사용 자산(`Button.tsx`)이 있어도 안 쓰여 중복이 쌓인다.

하네스는 이 결정들을 **미리, 한 번** 내려서 코드에 고정한다. 그래서 "누가 구현하느냐"가 결과를 바꾸지 못한다.

## 규칙의 근거 (요약)

- **`Button.tsx` 강제**: 이미 만든 디자인 시스템 버튼을 살린다. 스타일 일관성과 중복 제거.
- **`completed`를 타입에**: 완료는 데이터다. UI 임시 상태로 두면 정렬/필터 등 확장에서 깨진다.
- **콜백 네이밍 고정**: 컴포넌트 간 계약을 예측 가능하게. grep과 자동완성이 잘 먹는다.
- **상태를 `App.tsx`에**: 이 프로젝트의 단일 컴포넌트 모델(아키텍처 규칙)을 지킨다.
- **취소선 + 클래스**: 완료 표현을 하나로 통일해 CSS와 마크업이 갈리지 않게 한다.
